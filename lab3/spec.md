Main goal: побудувати детальні sequence-діаграми в Mermaid для кожного сценарію фокусного прецеденту UC-2 («Синхронізація метаданих») з 2 лаби на основі сутностей з 1 лаби (Character, Snake, Game).

Учасники взаємодії (Participants):
- Зовнішній актор: Konami Archive API ініціює запит PUT /api/v1/characters/{id}/sync.
- Компоненти системи: SyncController (REST-шлюз), LockCacheManager (керування блокуваннями записів та TTL-кешем на 24 години), SyncService (бізнес-логіка звірки статусів та конфліктів).
- Сутності даних (з 1 лаби): Character, Snake, Game.

Головні цілі:
- Провести попереднє опитування: ші аналізує спеку і перед генерацією діаграм ставить уточнюючі питання щодо деталей викликів та логіки розгалужень.
- Деталізувати внутрішню роботу системи для всіх 4 сценаріїв Gherkin прецеденту UC-2: Happy path (200 OK), Conflict path (200 OK з фіксацією has_canon_conflict = true), Lock / edge case (409 Conflict) та Error path (404 Not Found).
- Показати послідовність кроків кожного сценарію: захоплення блокування, перевірка існування персонажа, звірка final_status, оновлення сутностей та інвалідація кешу.

Вимоги та критерії прийняття:
- Побудувати 4 окремі sequence-діаграми в синтаксисі Mermaid sequenceDiagram (по одній на кожен сценарій UC-2, а не одну загальну).
- Узгодити учасників діаграм із сутностями з 1-ї лаби (Character, Snake, Game) та вимогами NFR/ADR з 2-ї лаби.
- Використати реалістичні назви викликів методів (наприклад, syncCharacter(), acquireLock(), findById(), updateStatus(), invalidateCache()) та обов'язкові зворотні повідомлення (return).
- Додати в кожну діаграму щонайменше один комбінований фрагмент (alt, opt або loop) для відображення перевірок, циклів або опціональних дій.
- Коректно оформити activation bars: якщо учасник працює до і після умовного фрагмента (alt/opt/loop), смуга активності починається до входу у фрагмент і закінчується після виходу з нього, а не обривається всередині гілки.
- Оформити прийняті архітектурні рішення в окремий ADR.
- Оголошувати в блоці participant лише тих учасників, які реально задіяні у конкретному сценарії (не додавати Snake та Game у сценарії 409 та 404).
- Для перевірок без альтернативної гілки (else) використовувати фрагмент opt замість одиночного alt, а текст умови робити коротким, щоб не ламати ширину рамки.
- Оформити прийняті архітектурні рішення в ADR за стандартом MADR: вказати розглянуті варіанти з плюсами та мінусами для кожного, драйвери рішення та наслідки.
