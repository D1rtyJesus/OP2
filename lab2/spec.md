Main goal: створити структуровані вимоги, Use cases та матрицю трасування для системи бази даних лору MGS на основі сутностей з першої лаби (Character, Snake, Game).

Актори системи:
- Людина: Reader (базовий читач) — переглядає загальний список ігор та таймлайн.
- Людина: Archivist (фанат лору / дослідник) — переглядає досьє персонажів, відстежує зв'язки між клонами та будує таймлайн ігор.
- Зовнішній сервіс: Konami Archive API (зовнішня система) — для синхронізації метаданих релізів та перевірки канонічності статусів.

Головні цілі:
- Провести попереднє опитування (Requirements Elicitation): ші виступає бізнес-аналітиком і перед генерацією вимог ставить уточнюючі питання стейкхолдеру щодо поведінки системи.
- Каталогізація та пошук персонажів за роллю, фінальним статусом та належністю до клонів Снейка.
- Побудова хронологічного порядку ігор (chron_order) незалежно від року релізу (release_year).
- Автоматична верифікація та синхронізація канонічних даних через зовнішнє API.
- Розписати вглиб прецедент «Синхронізація метаданих» (UC-2) з розширенням фіксації конфлікту та сценаріями на помилки/блокування.!!

Вимоги та критерії прийняття:
- Скласти EARS-вимоги з використанням 4 патернів: Ubiquitous (The system SHALL...), Event-driven (WHEN <тригер>, the system SHALL...), State-driven (WHILE <стан>, the system SHALL...), Optional (WHERE <умова>, the system SHALL...). Усі вимоги мають бути однозначними, без розмитих слів.
- Скласти окремий блок нефункціональних вимог (NFR) з чіткими числами: час відгуку, навантаження RPS, платформи та час життя кешу.
- Написати User Stories (As a... I want to... So that...) разом із приймальними тестами у форматі Gherkin (Given/When/Then).
- Побудувати Use Case діаграму в синтаксисі Mermaid. Показати акторів з їх узагальненням (Archivist наслідує Reader), використати зв'язки <<include>>, <<extend>> та узагальнення.!!
- Скласти матрицю трасування «вимога (EARS) - сценарій (UC)» у вигляді Markdown-таблиці. Зв'язки строго багато-до-багатьох (не 1:1). Обов'язково виділити мінімум 1 непокриту вимогу (Out-of-Scope) окремим блоком з поясненням.
- Оформити прийняті технічні рішення в окремий ADR.!!
